文档状态：候选方案，待验证、待决策

本文研究一种不部署 LessLive 常驻后端的方案：GitHub 作为社区后台，GitHub Actions 周期性汇总公开数据，静态站点展示星云。本文不替代社区规则，也不代表该方案已经批准实施。

## 1. 方案目标

LessLive 官网是 GitHub 社区的展示入口，不承担社区后台职责：

- 不提供站内账号、登录、认领、评论、点赞、私信或发帖；
- 不接收用户行为，不把网站访问当作入驻依据；
- 不复制 GitHub 成为第二套社区系统；
- 只展示 GitHub 上可读取的公开身份、仓库和社区行为；
- 允许数据按周期更新，不要求实时同步。

用户在 GitHub 上参与社区，GitHub 留下公开数据；LessLive 将这些数据汇总为星云快照，供更多人浏览。

## 2. 可行性结论

该方案在以下前提下可行：

1. 星云使用的数据都是 GitHub API 可读取的公开数据；
2. 节点点亮依据 GitHub 上发生的公开行为，而不是访问 LessLive 网站；
3. 可以接受定时快照带来的更新延迟；
4. 官网只做展示交互：悬停查看星云节点公开简介，点击跳转节点用户的 GitHub 仓库；
5. 不要求网站即时处理 OAuth 回调、节点操作或用户提交。

静态托管解决的是网站运行和展示问题。数据抓取、去重、关系计算仍然需要执行环境，由 GitHub Actions 承担，不需要自建常驻服务器。

## 3. 总体架构

```text
GitHub 组织、仓库、Discussions、公开行为
                    │
                    ▼
       GitHub Actions 定时/手动执行
       API 拉取、清洗、去重、关系计算
                    │
                    ▼
     lesslive/.github 中的 nebula.json
                    │
                    ▼
       GitHub Pages / 其他静态托管
                    │
                    ▼
         浏览器加载 JSON 并渲染星云
```

### 组件职责

| 组件 | 职责 |
| --- | --- |
| GitHub 组织与仓库 | 身份、内容、讨论、成员仓库和公开行为的事实来源 |
| `lesslive/.github` | 组织主页、官网内容、星云前端和发布快照的仓库候选 |
| GitHub Actions | 周期抓取、数据处理、快照校验和提交 |
| `nebula.json` | 面向前端的公开星云快照 |
| 静态托管 | 提供 HTML、CSS、JavaScript 和 JSON |
| 浏览器 | 加载快照、布局、动画和展示交互 |

## 4. `.github` 仓库边界

`.github` 是 GitHub 组织的特殊仓库，`profile/README.md` 是组织首页的自动渲染来源。它同时可以承载组织对外说明、加入方式、LessLive 理念、社区规则等官网静态内容。

候选目录：

```text
.github/                    # 本地开发文件夹为 LessLive/official，发布到 https://github.com/lesslive/.github
├── profile/README.md       # GitHub 组织首页
├── site/                   # 官网静态页面与资源
│   ├── index.html
│   ├── nebula/
│   │   ├── index.html
│   │   └── app.js
│   └── data/nebula.json    # Actions 生成的公开快照
├── scripts/                # 快照生成脚本
└── .github/workflows/      # Actions 工作流
```

该目录只是候选组织，最终是否把官网前端、社区文稿和快照放在同一发布目录，需要根据 GitHub Pages 的发布方式验证。仓库中的生成快照是公开汇总资产，不是私密数据；前提是脚本不得写入令牌、邮箱、私有仓库数据或不必要的个人字段。

## 5. 快照生成流程

GitHub Actions 支持定时和手动触发：

1. 检出 `.github` 仓库；
2. 使用 GitHub Actions 内置令牌或 GitHub App installation token 调用已验证的公开 API；
3. 拉取组织、目标仓库、Discussions、成员仓库及明确纳入范围的公开行为；
4. 按 GitHub 稳定 ID 去重，计算节点状态和关系；
5. 合并预设节点与已识别的 active 节点；
6. 校验 JSON schema、节点 ID、边端点和数据时间；
7. 只有快照发生变化时才提交 `nebula.json`；
8. 提交触发静态站点重新部署。

抓取失败、API 限流或结果校验失败时，不覆盖上一次有效快照；工作流应失败并留下可检查的日志。令牌只存放在 GitHub Actions Secrets 或 App 配置中，不进入仓库和前端。

## 6. 入驻与节点规则

“入驻”是运营叙事，不是网站交互动作。用户不需要在 LessLive 点击认领，也不需要填写资料。

云图入驻规则：**是否为 `lesslive` 组织成员决定是否映射节点；成员关系的可见范围不影响入驻资格。** GitHub 用户的成员可见性有两个选项：

- `Public`：所有 GitHub 用户都能看到该用户与组织的成员关系；
- `Member`：只有 `lesslive` 组织成员能看到该成员关系。

这两个选项控制成员关系对谁可见，不改变组织成员资格、仓库权限或 LessLive 入驻状态。设为 `Member` 的用户仍是组织成员，仍应映射到星云节点。

技术上，Actions 应读取 `lesslive` 的真实组织成员名单，而不能只依赖公开成员列表：

- 每个组织成员对应一个 active 节点；
- 非组织成员不因参与公开讨论或访问网站而自动获得节点；
- 节点不足时生成新的稳定节点，不让用户失败；
- 同一 GitHub 用户始终映射到同一节点；
- 节点分配和点亮结果写入快照或由可重建数据计算，不依赖网站会话。

成员关系的 `Public` / `Member` 可见性不是节点字段，也不作为是否展示节点的条件。星云展示所需资料来自 GitHub 用户公开资料；组织成员资格用于判定节点是否 active。

## 7. 指标来源与计算

本节定义星云中节点统计、关系强度和布局距离的来源与计算方式。抓取范围为 `lesslive/opc.os` 的公开 Discussions；只有当前 `lesslive` 组织成员映射为星云节点。API 对象按 GitHub 稳定 ID 去重。

### 节点指标

| 指标 | 含义 | 来源与计算 |
| --- | --- | --- |
| `post_count` | 成员发帖数 | 该成员作为作者发布的 Discussion 数；按 Discussion ID 去重 |
| `comment_count` | 成员评论数 | 该成员作为作者发布的 Discussion 评论数，包含顶层评论和对评论的回复；按评论 ID 去重 |
| `relationship_count` | 关系对象数，即成员的圈子人数 | 与该成员发生过至少一次有效直接回复互动的不同组织成员数；按对端 GitHub 用户 ID 去重 |

发帖数、评论数和关系对象数是不同指标。发帖本身不增加评论数；同一对象之间多次回复仍只让 `relationship_count` 增加 1，但会增加两人之间的互动频次。

### 关系对象与互动频次

只把有明确对象的直接回复计作关系互动：

- Discussion 的顶层评论以该 Discussion 作者为互动对象；
- 对评论的回复以被回复评论的作者为互动对象；
- 互动双方必须都是当前 `lesslive` 组织成员，且不能是同一人；
- 仅在同一 Discussion 下各自发言、彼此没有直接回复，不建立两人之间的边；
- 一条评论或回复按其 GitHub 评论 ID 计 1 次，重复分页、重复抓取或编辑不重复计数。

边按无向用户对聚合。例如 A 回复 B 5 次、B 回复 A 2 次，则 A 与 B 之间只有一条边，`interaction_count` 为 7；双方各自的 `relationship_count` 都只增加 1。方向可在内部统计时保留，但当前快照只需输出双向总频次。

### 边权重与节点距离

`interaction_count` 是边的行为权重，直接等于该用户对去重后的有效回复数量。它不代表亲密程度或关系质量。

云图布局距离由互动频次单调递减计算。候选公式为：

```text
target_distance = min_distance
                 + (max_distance - min_distance)
                 / (1 + ln(interaction_count))
```

其中 `interaction_count >= 1`。互动 1 次时目标距离为 `max_distance`；互动增加时目标距离逐渐靠近 `min_distance`，对高频互动使用对数压缩，避免极高次数把节点挤到一起。`min_distance` 和 `max_distance` 是前端布局参数，不是关系事实；需通过实际图谱效果校准。没有互动边的节点对不计算目标距离，由布局引擎按整体布局规则放置。

该距离只控制可视化布局，不改变关系是否存在，也不输出为“亲密度”。预设随机展示边若仍用于画面，其布局规则与真实互动边分开处理，不计入上述互动频次或关系对象数。

### 删除与时间边界

当前计算口径是 API 抓取时仍可读取的公开 Discussion 和评论。评论编辑按原评论 ID 计一次；评论删除后是否从历史互动频次中撤销，尚待验证 GitHub API 的可发现方式和产品规则。初次上线时应记录快照生成时间，并明确统计是历史累计还是限定时间窗口；时间窗口尚未决定前不应把指标标成“近期活跃度”。

## 8. 快照数据边界

快照只提供官网展示所需字段，示例：

```json
{
  "generated_at": "2026-11-05T00:00:00Z",
  "nodes": [
    {
      "id": "node-001",
      "status": "active",
      "github_login": "example",
      "display_name": "Example",
      "avatar_url": "https://avatars.githubusercontent.com/...",
      "github_url": "https://github.com/example",
      "repository_url": "https://github.com/lesslive/example",
      "metrics": {
        "post_count": 3,
        "comment_count": 8,
        "relationship_count": 4
      }
    }
  ],
  "edges": [
    {
      "source": "node-001",
      "target": "node-002",
      "source_type": "github_activity",
      "interaction_count": 7,
      "target_distance": 18.4
    }
  ]
}
```

不输出 OAuth 令牌、App 私钥、邮箱、私有仓库、评论正文或与展示无关的个人字段。公开 GitHub 数据不等于可以无限复制；采集范围应保持最小，字段用途应能解释。

## 9. 前端与部署

前端是普通静态资源：HTML、CSS、JavaScript、图片和 `nebula.json`。浏览器加载同源快照后完成：

- 节点和边布局；
- 节点亮度、状态和动画；
- 鼠标悬停显示公开简介，以及发帖、评论、关系数量等信息
- 点击跳转到 GitHub 用户主页或成员仓库。

前端不直接调用 GitHub API，不持有 PAT、App 私钥或用户访问令牌。D3、AntV G6、Three.js 等只负责浏览器渲染，不承担数据采集。

静态托管候选包括 GitHub Pages、Cloudflare Pages 和 Vercel 静态部署。选择依据是域名、构建方式、缓存刷新和 GitHub 仓库集成，不是渲染能力。

## 10. GitHub App 与 Actions 的关系

GitHub App 可以作为 Actions 抓取 GitHub 数据的细粒度身份来源，也可以为未来事件监听提供能力。但采用周期快照时不需要 Webhook；Webhook URL、常驻后端和 ngrok 都不是本方案的必需组件。

在未验证实际 API 权限前，不预先扩大 App 权限。优先使用公开读取能力；确需安装令牌时，只申请目标仓库和当前数据范围所需的只读权限。

## 11. 与常驻后端方案的差异

| 能力 | 全静态方案 | 常驻后端方案 |
| --- | --- | --- |
| 官网展示 | 支持 | 支持 |
| 周期更新 | 支持 | 支持 |
| 实时更新 | 不支持 | 可支持 |
| 网站登录和会话 | 不支持 | 可支持 |
| 网站提交数据 | 不支持 | 可支持 |
| GitHub 行为抓取 | Actions 完成 | 服务端完成 |
| 数据库 | 不需要 | 通常需要 |
| 常驻服务器 | 不需要 | 需要 |
| 运维复杂度 | 低 | 高 |

## 12. 必须验证的问题

1. 组织 `.github` 仓库能否按预期同时承载组织首页、官网内容、前端和快照发布流程。
2. GitHub Pages 的源目录、构建方式、自定义域名和刷新延迟是否满足要求。
3. GitHub API 能否读取完整的 `lesslive` 组织成员名单，包括成员关系可见性设为 `Member` 的成员。
4. GitHub App 或 Actions token 对读取组织成员名单及目标公开数据需要哪些最小权限。
5. Discussion 评论及回复字段是否足以按上述口径准确解析回复对象；删除评论的发现与撤销规则是什么。
6. 统计采用历史累计还是时间窗口；距离参数如何按实际布局校准。
7. GitHub 用户改名、退出组织、删除仓库、删除讨论后，快照如何更新。
8. Actions 定时频率、API 限流、失败重试和提交频率是否足够。
9. 快照公开发布的字段范围是否满足隐私和运营边界，尤其是成员关系设为 `Member` 时的展示规则。

## 13. 实施顺序建议

### 阶段 0：能力验证

用测试仓库和测试账号验证目标 GitHub API、App 权限、Actions 定时执行和 Pages 发布，不编写完整星云逻辑。

### 阶段 1：静态展示原型

手工准备一份 `nebula.json`，完成静态页面、节点状态、悬停简介和 GitHub 跳转。

### 阶段 2：自动快照

实现抓取脚本、schema 校验、Actions 工作流和只在数据变化时提交的流程。

### 阶段 3：真实规则

确定入驻行为和关系规则，加入稳定 ID、幂等、异常保留旧快照和删除行为处理。

### 阶段 4：发布决策

根据验证结果选择 GitHub Pages、Cloudflare Pages 或 Vercel，并配置域名和缓存策略。

## 14. 方案结论
全静态托管是一个可行的候选架构，适合 LessLive“GitHub 是后台、官网只展示、允许周期更新”的方向。它的核心限制不是图形渲染，而是 GitHub API 能否提供足够的公开数据，以及入驻和关系规则能否用这些数据稳定表达。

在完成第 11 节验证前，本方案不应被当作最终技术决策；现有 Go、PostgreSQL、OAuth 和 Webhook 方案也不应被自动保留或自动废弃。
