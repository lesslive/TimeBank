## 目的与前提

[[资产管理]]负责判断什么可以进入仓库、内容应当符合什么要求，以及由哪个模块负责。本指南负责将这些判断落实为文件操作：创建、更新、组织、引用、移动、重命名与清理。

操作前，应已明确内容的用途、归属及本次处理方式。尚未确定的，先按资产管理要求判断，不通过先建文件、放到根目录或新建收件箱来回避。

模块入口已有的组织要求优先适用。本指南提供通用操作方法，不要求所有模块采用同一种目录或文档结构。

## 创建与更新

1. **确认目标模块**：阅读模块入口、编写规范及必要的示范，确定目标目录和已有编写要求。
2. **检索相关内容**：在相关模块中检索标题、关键词及引用关系，打开候选文件核对内容。可以借助 Smart Connections 的相似内容面板发现关联，但不依赖插件才能执行，也不按相似分数直接判定重复。
3. **落实处理方式**：需要补充或修正的，在已有文件中更新；只需使用已有结论的，建立引用；已确认具有独立用途且需要新建的，再创建文件。是否应新建，依据资产管理的判断，不以搜索不到完全同名文件作为唯一理由。
4. **按规范编写**：使用能表达主题的名称，在确定的目录中创建 Markdown 文件。按模块规范、模板或示范组织正文及 frontmatter，不擅自增加必填字段，不为填满格式编造内容。
5. **保留有效记录**：更新已有文件时，保留仍有效的内容、创建信息和必要关联；调整内容时同步维护适用的更新时间、状态及引用。不擅自给用户文件添加 `model` 或 `example` 标签。
6. **核对写入结果**：确认实际路径、文件内容和相关链接正确，新建文件没有与已有文件或目录发生冲突，更新没有覆盖无关内容。
7. **用 Git 管理版本**：同一资产只维护一份正文，直接在原文件中更新，不创建“v1、v2、修改版、最终版”等版本副本。历史修订、差异比较和恢复交给 Git；不同用途的派生内容不属于版本副本。

Git 的提交历史只记录已经提交的修改，仅保存文件并不会产生提交记录。提交前检查实际变更，确认其中没有无关或意外改动。

## 主题内组织

### 文件夹笔记

与所在目录同名、位于该目录内的 Markdown 文件，称为文件夹笔记。例如，`内驱力/内驱力.md` 是 `内驱力` 目录的文件夹笔记。

文件夹笔记可以承担模块入口或主题内容两种职责。作为主题内容时，可以是草稿或正文，是该主题的核心内容，同目录的派生文档以它为依据。名称和位置只说明它的组织形式，具体用途由内容及模块要求决定。

在 Obsidian 中，点击目录直接打开同名笔记的体验，取决于所使用的文件夹笔记插件或相关设置；未启用时，可以直接打开目录内的同名文件。

### 模块入口

文件夹笔记作为入口描述时，用于说明模块的定义、职责、边界、组织方式和使用注意事项。例如：

```text
第一课题/
├── 第一课题.md          # 第一课题的入口描述
├── 内驱力/
│   └── 内驱力.md        # 内驱力组件的入口描述
├── 主体性/
│   └── 主体性.md        # 主体性组件的入口描述
└── 生命力/
    └── 生命力.md        # 生命力组件的入口描述
```

使用已有模块时先读入口，不把与入口职责无关的具体内容、临时任务或个人实践直接追加其中。修改入口仍须遵守该文件的保护规则。

### 主题内容与派生文件

一个已确认需要持续扩展的主题，可以采用主题目录组织原始内容与派生文件。目录同名笔记承载主题内容草稿或原始论述，其他文件承载面向不同对象、渠道或用途的表达。

```text
马瑟兰的品牌故事/
├── 马瑟兰的品牌故事.md  # 主题原始内容
├── 直播间.md            # 直播口播与互动方案
├── 公众号.md            # 公众号文章
├── 视频号.md            # 短视频脚本与口播文案
├── 活动方案.md          # 围绕该主题设计的活动方案
└── 朋友圈.md            # 朋友圈图文
```

这是组织示例，不是必须一次建齐的文件清单。只创建当前确有用途的文件；模块要求使用单个文件时，不自行改成主题目录。

将已有单篇文件转换为主题目录时，先确认目标路径，再创建目录，通过 Obsidian 将原文件移入，保持文件与目录同名，最后检查原有引用。不要在新目录复制一份正文、再让新旧两份同时维护。

## 引用与派生

- **引用已有内容**：需要使用已有事实、观点或策略时，使用 Obsidian 内部链接；只涉及其中一部分的，可链接到对应标题。原内容仍在原文件维护，不为每个使用场景再保存一份相同正文。
- **形成派生表达**：根据对象、渠道或用途加工后的内容，按已确认的归属创建或更新，并保留到来源的必要引用。派生文件负责自己的表达，不替代原文件承担原有职责。
- **区分引用与迁移**：愿景、使命、主张等内容仍承担原有功能时，留在原位置，由其他模块引用和加工；只有内容用途已经改变、归属需要调整时，才执行迁移。
- **连接运行安排**：文件涉及的制作、发布或其他行动，由相关[[旅程]]或看板引用安排，不在多个内容文件中复制维护同一套任务进度。保存内容本身不自动产生待办。

## 变化与迁移

确定需要改变归属、调整名称或合并内容后，按以下流程操作：

1. **确认操作范围**：列明源路径、目标路径、需保留的内容，以及可能受影响的引用。目标已存在时，先判断如何处理，不直接覆盖。
2. **移动或重命名**：需要调整路径时，通过 Obsidian 的移动或重命名功能处理文件与目录，并按链接更新设置维护引用；不以复制后删除代替移动。
3. **合并内容**：需要合并时，先把有效内容及必要来源整合到目标文件，核对原文件的独立内容是否仍需保留，再处理原文件与引用。不因主题相近就自动合并。
4. **检查操作结果**：确认新路径及内容正确，检查入口、正文链接、标题链接，以及旅程、看板或派生文件中的相关引用。需要手动修正的引用一并处理，不留下指向旧路径的无效链接。

主题目录或目录同名文件发生名称变化时，同时核对它们的命名关系，避免目录与入口意外脱节。

## 更新与结束

- **持续完善**：在已有文件中补充和修订，不为每次编辑另建一份副本。旧版本通过 Git 历史查阅，不另存为“历史方案”；具有独立用途的方案与实践记录可以分别保留，按模块规范标明状态，不把已失效的内容当作当前依据。
- **暂停或结束**：按模块规范更新状态，保留有复盘价值的方案与实践记录，不因项目暂停就删除全部相关文件，也不为避免遗忘自动增加提醒。
- **归档**：模块已有归档方式且已确认需要归档的，按该方式处理；归档涉及移动时，同样执行迁移与引用检查，不另建一套重复的历史副本。
- **删除**：确定文件不再需要独立保留后，先检查是否存在仍需保留的独有内容及引用，再通过 Obsidian 的删除或回收机制处理。相关引用应改指有效目标或移除；永久删除需另行明确选择，不批量清理用途尚未确认的文件。

## AI 操作要求

> [!ai]- AI
> - 先按[[资产管理]]确认内容与处理方式，再执行本指南。讨论或整理建议不等于操作授权，明确授权后在对应范围内执行。
> - 关注相关模块的局部 AI 说明。Git 版本管理不等于自动提交授权；未经用户明确确认，不提交或推送。
> - 不自行改写带 `model` 标签的文件；官方系统升级按[[系统升级]]的授权与流程执行。目录同名文件不因组织形式而一律禁止修改，仍按文件自身的标签和保护规则判断。
> - 涉及移动、重命名、合并或删除时，确认授权覆盖该操作，再核对目标和引用；不因路径冲突覆盖目标文件，不处置用户的无关改动。应用或链接维护能力不可用时，说明阻碍，不擅自换用绕过链接维护的操作。
> - 完成后核对实际内容、路径和受影响的引用，简要说明执行结果及未解决事项。不把内容保存等同于任务推进、对外发布或现实验证已经完成。
