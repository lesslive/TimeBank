## 目的与原则

文件管理首先是为了不消耗自己，通过将记录、归位、加工进行解耦，让想法被及时保存，不打断当前正在做的事，并在需要的时候能找到它。
## 创建与归位

一个想法出现时，只做最少必要的记录：

1. **判断归属**：直接找到对应的所属模块，否则，就放在根目录，不继续翻找或纠结。
2. **创建文件**：构思一个能够用来创建文件、帮助自己辨认这个想法的名字并创建。
3. **记录内容**：记录想法，然后关闭退出。甚至允许正文为空，不为完成而延长记录。

### 允许忘记它
只要它在正确的位置，需要的时候，自然会与它重逢，否则，就是缘分未到。是否加工不影响这一点。尚未完善，通常只是还没到使用它的时候，不代表需要催办、补齐或删除。
### 再次发现它
真正需要相关内容时，人和 AI 会到对应模块查找，已有想法便有机会再次被发现。需要时再读、再判断、再加工，不为防止遗忘而把每个文件变成提醒或待办。
### 清空根目录
如果它在根目录，应该尽快为它找到归属位置，甚至可以判断它根本就是多余的，应该立刻删除。可以临时允许它破坏仓库根目录形状，但不应该长期在这里保存。
## 加工与更新

**加工的最好时机是需要使用它的时候，而不是先加工好，再等以后确定用途。**

围绕当前实际需要，先到相关模块查找已有想法和成果，再按需要执行以下操作：

1. **明确当前用途**：阅读相关模块入口、规范及必要示范，确定这次要解决什么问题、怎样使用已有内容。归属有变化的，重新判断位置。
2. **检索相关内容**：在相关模块中检索标题、关键词及引用关系，打开候选文件核对内容。可以借助 Smart Connections 的相似内容面板发现关联，但不依赖插件才能执行，也不按相似分数直接判定重复。
3. **落实处理方式**：需要补充或修正的，在已有文件中更新；只需使用已有结论的，建立引用；已确认具有独立用途且需要新建的，再创建文件。是否应新建，依据资产管理的判断，不以搜索不到完全同名文件作为唯一理由。
4. **按照规范编写**：使用能表达主题的名称，在确定的目录中创建 Markdown 文件。按模块规范、模板或示范组织正文及 frontmatter，不擅自增加必填字段，不为填满格式编造内容。
5. **保留有效记录**：更新已有文件时，保留仍有效的内容、创建信息和必要关联；调整内容时同步维护适用的更新时间、状态及引用。不擅自给用户文件添加 `model` 或 `example` 标签。
6. **核对写入结果**：确认实际路径、文件内容和相关链接正确，新建文件没有与已有文件或目录发生冲突，更新没有覆盖无关内容。
7. **用Git管理版本**：同一资产只维护一份正文，直接在原文件中更新，不创建“v1、v2、修改版、最终版”等版本副本。历史修订、差异比较和恢复交给 Git；不同用途的派生内容不属于版本副本。

## 原生与派生

与所在目录同名、位于该目录内的 Markdown 文件，称为文件夹笔记，承担目录入口职责，可以是草稿或正文，是该目录的原生内容，根据不同场景派生不同文档。例如：

```text
我的品牌故事/
├── 我的品牌故事.md  # 主题原始内容
├── 直播间.md            # 直播口播与互动方案
├── 公众号.md            # 公众号文章
├── 视频号.md            # 短视频脚本与口播文案
├── 活动方案.md        # 围绕该主题设计的活动方案
└── 朋友圈.md            # 朋友圈图文
```

## 变化与迁移

确定需要改变归属、调整名称或合并内容后，按以下流程操作：

1. **确认操作范围**：列明源路径、目标路径、需保留的内容，以及可能受影响的引用。目标已存在时，先判断如何处理，不直接覆盖。
2. **移动或重命名**：需要调整路径时，通过 Obsidian 的移动或重命名功能处理文件与目录，并按链接更新设置维护引用；不以复制后删除代替移动。
3. **合并内容**：需要合并时，先把有效内容及必要来源整合到目标文件，核对原文件的独立内容是否仍需保留，再处理原文件与引用。不因主题相近就自动合并。
4. **检查操作结果**：确认新路径及内容正确，检查入口、正文链接、标题链接，以及旅程、看板或派生文件中的相关引用。需要手动修正的引用一并处理，不留下指向旧路径的无效链接。

主题目录或目录同名文件发生名称变化时，同时核对它们的命名关系，避免目录与入口意外脱节。

## 更新与删除

- **按需完善**：使用时在已有文件中补充和修订，不要求定期加工全部文件，不因已归位的文件空白、简短或长期未编辑就视为积压。旧版本通过 Git 历史查阅，不另存为“历史方案”；具有独立用途的方案与实践记录可以分别保留，按模块规范标明状态，不把已失效的内容当作当前依据。
- **暂停或结束**：按模块规范更新状态，保留有复盘价值的方案与实践记录，不因项目暂停就删除全部相关文件，也不为避免遗忘自动增加提醒。
- **归档**：模块已有归档方式且已确认需要归档的，按该方式处理；归档涉及移动时，同样执行迁移与引用检查，不另建一套重复的历史副本。
- **删除**：确定文件不再需要独立保留后，先检查是否存在仍需保留的独有内容及引用，再通过 Obsidian 的删除或回收机制处理。相关引用应改指有效目标或移除；永久删除需另行明确选择，不批量清理用途尚未确认的文件。

## AI操作规范

> [!ai]- AI
> - 区分快速记录与按需加工。用户只要求记下想法时，按已知归属安放，无法确定则暂存根目录，不为了填模板、补背景或研究价值而延长任务；需要加工时再结合[[资产管理]]及模块规范判断。
> - 已归位的想法不因尚未加工而成为待办，不自动批量补写空文件、催促完善或清理长期未使用的内容。根目录暂存的去留可在相关清理任务中处理，不每次会话都强制清空。
> - 讨论或整理建议不等于操作授权，明确授权后在对应范围内执行。授权快速记录，不等于授权进一步研究、制定计划或执行想法。
> - 关注相关模块的局部 AI 说明。Git 版本管理不等于自动提交授权；未经用户明确确认，不提交或推送。
> - 不自行改写带 `model` 标签的文件；官方系统升级按[[系统升级]]的授权与流程执行。目录同名文件不因组织形式而一律禁止修改，仍按文件自身的标签和保护规则判断。
> - 涉及移动、重命名、合并或删除时，确认授权覆盖该操作，再核对目标和引用；不因路径冲突覆盖目标文件，不处置用户的无关改动。应用或链接维护能力不可用时，说明阻碍，不擅自换用绕过链接维护的操作。
> - 完成后核对实际内容、路径和受影响的引用，简要说明执行结果及未解决事项。不把内容保存等同于任务推进、对外发布或现实验证已经完成。
